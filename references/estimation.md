# 规模估算：Back of the Envelope

目的：用一支笔的精度回答"这个系统到底要多大的架构"，据此选择架构档次，防止**设计不足**（上线即崩）和**过度设计**（三个用户上 K8s）。允许 10 倍以内的误差，精确到数量级即可。

## 一、常用数字速查（记结论不推导）

| 操作 | 量级 |
|---|---|
| 一次内存随机读写 | ~100ns |
| 一次 SSD 随机读写 | ~100μs（比内存慢 1000 倍） |
| 同机房网络往返 | ~0.5ms |
| 跨地域网络往返 | ~50-150ms |
| 单核处理简单 JSON API 请求 | 数千 QPS |
| 单台 4C8G 机器的普通 CRUD API | 500-2000 QPS（视复杂度） |
| PostgreSQL 简单查询（有索引） | 单机数千 QPS |
| 一页 HTML/JSON 响应 | 5-100 KB |

推论：**多数应用撑不住的从来不是计算，而是数据库**。估算的重点是读写 QPS 落到数据库多少、数据量多大。

## 二、推算链

从业务量倒推技术量，每一步把假设写明（假设要进蓝图，错了好修正）：

### 1. 用户量 → DAU
- 注册用户 ≠ 活跃用户。问业务方或拍一个比率（外部产品 DAU/注册 ≈ 10-30%，内部工具 ≈ 80-100%）。

### 2. DAU → 峰值 QPS
```
人均请求数 × DAU ÷ 86400 秒 = 平均 QPS
平均 QPS × 峰值系数 = 峰值 QPS
```
- 人均请求数：按核心场景数一次交互 5-20 个 API 请求估。
- 峰值系数：日常 2-3 倍；有定时任务/整点开放/促销抢购的场景单独算（那一刻的 QPS 可能是平均的 50-100 倍，必须点名）。
- 读写分离：CRUD 应用读:写典型 10:1 到 100:1（刷得多、写得少），据此拆出读 QPS 和写 QPS。

### 3. 存储量
```
单条记录大小 × 每日新增条数 × 365 × 保留年数 × 副本/索引膨胀系数(2-3)
```
- 别忘了增长最快的通常是"内容类"数据（图片/附件）：单张图 0.5-5 MB，一乘就是 GB/T 级。图片视频考虑对象存储而非数据库 BLOB。

### 4. 带宽
```
峰值 QPS × 平均响应大小 = 出口带宽
```
- 1000 QPS × 50 KB ≈ 50 MB/s ≈ 400 Mbps——够买多大带宽心里有数了。

## 三、档次结论表

算完对号入座。**选最够用的最低档**，升档路径留好（见 patterns.md 演进策略）：

| 档次 | 特征 | 典型配置 |
|---|---|---|
| L1 单机 | 峰值 QPS < 50，DAU < 1千，存储 < 10 GB | 单机或 PaaS：应用 + PostgreSQL/SQLite + 对象存储（如有文件） |
| L2 单机+缓存 | QPS 50-500，DAU 千-万，读多写少 | 应用（可双实例）+ PostgreSQL + Redis + 对象存储 + CDN（如有静态资源压力） |
| L3 读写分离水平扩展 | QPS 500-5000，DAU 万-百万 | 应用无状态多实例 + PostgreSQL 主从 + Redis + 消息队列（削峰/异步任务）+ 负载均衡 |
| L4 分布式 | QPS > 5000 或强隔离需求 | 按域拆服务 + 分库分表/分布式存储 + 全链路监控。**没有 L3 撞墙的实测证据不要选它** |

## 四、输出要求

把估算写进蓝图"规模估算"章节，格式：

```
假设：DAU 5000，人均 15 请求，峰值系数 3，读:写 = 20:1
推算：平均 QPS ≈ 0.9，峰值 QPS ≈ 2.6（其中写 ≈ 0.12）
存储：文章 2KB/篇 × 500 篇/天 × 365 × 3 年 × 2 ≈ 2.2 GB；图片 1MB/张 × 200 张/天 ≈ 220 GB/年 → 对象存储
带宽：峰值 2.6 × 50KB ≈ 130 KB/s —— 忽略不计
结论：档次 L2。无秒杀/定时洪峰场景。
难点标注：文章全文搜索若成为核心场景需引入搜索组件（REQ-014 相关）。
```

**难点标注**是估算环节最有价值的产出：它把"哪些需求因此变难"点名，直接驱动 Phase 6 的针对性设计。常见难点：秒杀/抢购（热点行）、全文搜索、大文件上传下载、报表聚合（大表扫描）、实时推送（长连接）、跨时区时间处理、第三方限流。

## 五、红线提醒

- 估算结果**决定架构档次，而不是反过来**。先写了"用微服务"再回头找数字支撑是本末倒置。
- 内部工具/管理后台几乎总是 L1-L2——别被"我们用户很多（全公司 2000 人）"吓到。
- 用户声称的量级和真实量级经常差 10 倍以上，取保守值起步，架构留好升档路径比一开始就拉满便宜得多。
