# 非功能设计：质量属性、安全与失效模式

非功能设计**按 Phase 2 的档次裁剪**：L1 项目不需要容灾演练，但下面"安全底线"一节无论多小的项目都完整执行。

## 一、六个质量属性及常用手段

| 属性 | 度量方式 | 常用手段（按档次递进） |
|---|---|---|
| 性能 | P95/P99 延迟、QPS | 索引 → 缓存热点读 → 异步化慢操作 → 读写分离 |
| 可用性 | 全年可用时长（99.9% ≈ 年停 8.7h） | 单机重启自愈 → 双实例+健康检查 → 多可用区 |
| 可扩展性 | 流量翻倍要做什么 | **无状态应用**（前提）→ 水平加实例 → 拆读写 → 拆服务 |
| 安全 | 漏洞清单、审计覆盖 | 见下节安全底线 |
| 可维护性 | 新人上手时间、改动波及面 | 模块化、自动化测试、文档与代码同处一仓 |
| 数据完整性 | 丢数据窗口 | 事务 → 每日备份 → 备份可恢复演练 → 主从复制 |

方法：对每条非功能需求（NFR-xxx）标注"用什么手段满足 + 如何验证"。写不出验证方式的属性承诺等于没承诺。

## 二、安全底线（任何档次都必做）

1. **认证**：用成熟方案（JWT/Session + 成熟库），不自研密码学。密码 bcrypt/argon2 哈希，绝不存明文/MD5。
2. **授权**：每个接口显式声明鉴权要求（API 清单的"鉴权"列），后端逐接口检查，禁止"前端藏了入口就算鉴权"。
3. **输入校验**：所有外部输入（query/body/header）过 schema 校验（zod/pydantic/joi 等），拒绝而不是修剪非法输入。
4. **注入防护**：一律参数化查询（ORM 默认安全，手写 SQL 是风险点）；XSS 靠模板转义/CSP；CSRF 靠 token 或 SameSite cookie。
5. **密钥管理**：`.env` 入 `.gitignore`，提供 `.env.example`；任何密钥泄露进 git 历史 = 已泄露，直接轮换。
6. **传输**：HTTPS，本地开发除外。
7. **最小权限**：数据库账号不给 superuser；云资源按最小 IAM 权限。

安全需求的追溯：把上述条目对应到 NFR 编号或蓝图安全章节的 checklist，验收时逐条核对。

## 三、失效模式分析（对每个关键组件问"挂了会怎样"）

对清单里的每一项，写出：故障表现 → 用户看到什么 → 恢复手段 → 是否接受风险。

组件清单起点：数据库挂、缓存挂、第三方 API 挂/超时/限流、对象存储挂、消息队列积压、应用实例 OOM、磁盘写满、证书过期、依赖服务（DNS/网关）故障。

常见问题的标准答案（写不出的照抄）：

- **第三方支付回调没收到** → 主动对账定时任务兜底，不依赖回调必达。
- **缓存挂了** → 应用直连数据库应能存活（可能慢），缓存做旁路（cache-aside）不是强依赖。
- **第三方 API 超时** → 超时 5-10s + 指数退避重试（只重试幂等操作）+ 失败落表人工/定时补偿；用户侧给明确失败提示，不是无限转圈。
- **数据库连接打满** → 连接池上限 + 慢查询监控；L3 以上考虑连接中间件。
- **流量翻 10 倍** → 档次结论是否还成立？不成立的话触发什么预案（扩容脚本/降级非核心功能/排队）。

明确写出"接受的风险"是合法结论："L1 项目数据库挂了恢复靠重启+备份恢复，RTO 1 小时，接受"——比假装它不会发生好。

## 四、性能设计要点（只针对估算标出的难点）

- 缓存用 cache-aside 模式：读 → 缓存未命中查库回填；写 → 先写库再失效缓存。缓存 key 和 TTL 策略写明。
- N+1 预防：ORM 关联查询统一用预加载（eager loading），code review 必查项。
- 大导出/大计算：一律异步任务 + 进度可查，不允许 HTTP 请求里同步跑 30 秒以上。
- 慢查询日志从第一天打开（如 PostgreSQL `log_min_duration_statement=500ms`）。
