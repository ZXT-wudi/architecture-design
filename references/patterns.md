# 架构风格选型与代码组织

## 一、架构风格决策表

五种主流风格，按"什么时候才有资格用"排列。**默认永远是前两种之一**：

| 风格 | 是什么 | 什么时候选 | 什么时候别选 |
|---|---|---|---|
| **单体**（monolith） | 一个进程一个部署单元 | L1 档次；个人/小团队；任何 MVP | 基本没有"别选"的场景，团队 > 30 人才需要考虑拆 |
| **模块化单体**（modular monolith） | 单进程，但内部按业务域切成边界清晰的模块，模块间只走公开接口 | **L1-L3 的默认答案**；预期会成长的系统 | 几乎没有 |
| **微服务** | 按业务域拆成独立部署的服务 | 独立扩展/独立发布/独立团队三样至少占两样且是真实痛点 | 团队 < 15 人；没有容器编排与可观测经验；流量根本没到（L4 之前） |
| **Serverless** | 函数即服务，按调用计费 | 流量极不均匀（一天几十个请求）；纯事件触发任务 | 有长连接/WebSocket；冷启动敏感；状态复杂 |
| **事件驱动** | 组件间通过事件/消息异步协作 | 削峰、跨域解耦、多方消费同一事件 | 业务流程强依赖同步结果（下单必须立刻知道成没成） |

### 微服务的资格清单（三条全占才谈）

1. 不同模块的负载差异大到需要独立扩缩容（如导出服务吃 CPU 但主站不吃）。
2. 不同模块需要独立发布节奏且有足够人力并行（两个团队以上）。
3. 有能力承担分布式全套税：服务发现、链路追踪、分布式事务、运维成本翻倍。

反例提醒：**"以后用户多了要拆"不是微服务的理由**。模块化单体保留清晰边界，真到那天按模块拆出去，正是它的设计目的。

## 二、代码组织（模块内部怎么写）

确定风格后，选模块内部的代码组织方式：

| 方式 | 一句话 | 适用 |
|---|---|---|
| 简单分层 | controller → service → repository，从上往下单向依赖 | CRUD 为主的模块，默认起点 |
| 六边形/端口适配器 | 业务核心不依赖任何框架和外部细节，外部通过 port 接入 | 业务规则复杂、需要频繁换外部依赖（换库/换支付渠道）的模块 |
| Clean Architecture | 分层 + 依赖倒向内的严格规则 | 与六边形同族，术语更重，中小项目用简单分层+好接口设计即可 |
| DDD 战术模式 | 实体/值对象/聚合/领域事件，按限界上下文划分 | 业务规则极度复杂且与领域专家需要持续对话时；多数项目只需要它的"限界上下文"思想来做模块划分 |

选择建议：**默认简单分层**。当某个模块的业务规则开始膨胀、单测要 mock 一堆框架组件时，只对该模块升级为六边形。一个项目里允许混合。

## 三、模块划分方法

1. **按业务能力切，不按技术层切**。"订单""库存""通知"是好模块名；"models""utils""services"是坏模块名（技术分层放模块内部，不放模块之间）。
2. **每个模块一句话职责**：写不出来说明边界没想清楚，继续拆或合并。
3. **依赖方向单一**：画依赖箭头，出现环就是边界错了。跨模块调用只走对方公开的接口（API/服务接口），不许直接摸对方的表和内部函数。
4. **共享的东西放 shared/，且要克制**：一旦 shared/ 变成垃圾场，模块化就名存实亡。
5. **对账**：把需求追踪矩阵里 REQ → 模块的映射拿出来看一眼——一个模块承载了 60% 以上需求说明切分失衡。

## 四、演进策略（现在怎么设计，将来怎么变）

- 单体 → 扩容：加机器副本（前提：应用无状态——session 外置、文件进对象存储。**无状态是现在就必须做的设计**）。
- 模块化单体 → 微服务：按模块整体搬走，模块间 HTTP 调用替换原进程内调用。这就是为什么模块边界和"只走公开接口"现在要守住。
- 读库扛不住 → 主从分离 + 读库（应用侧先做好读写路由的抽象）。
- 单表太大 → 先分区/归档，再谈分库分表。
- 同步调用成瓶颈 → 引入消息队列做异步化，先从非核心路径（通知、日志、导出）开始。

把"预留的演进路径"写进蓝图"演进路线"章节——它说明现在的哪些设计决定是为了将来哪个升级做准备，防止将来的人破坏前提而不自知。

2. 模块清单：名称 + 一句话职责 + 依赖方向。
