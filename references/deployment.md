# 部署与运维

按档次裁剪：L1 用 PaaS 或单机 Docker Compose 就是正确答案，不丢人。

## 一、环境划分

最少两个环境，第一天就分：

| 环境 | 用途 | 数据 |
|---|---|---|
| dev | 本地开发 | 本地数据库 + docker compose / 测试夹具 |
| prod | 真实用户 | 真实数据 + 备份 |

有真实用户后再加 staging（类生产预发，跑 E2E 和发布演练）。**禁止直接在 prod 手工改库**——变更一律走迁移脚本（migration），迁移脚本进代码仓库。

## 二、部署方式按档次选

| 档次 | 方式 | 说明 |
|---|---|---|
| L1 | PaaS（Vercel/Railway/Render）或 VPS + Docker Compose | 一条命令部署；数据库用云托管（RDS/云 PG），别在应用机上自装数据库然后忘了备份 |
| L2-L3 | 云主机 ×2 + Docker Compose + Nginx/Caddy 负载均衡，或云托管 K8s | 应用无状态化后双实例 + 健康检查 |
| L4 | K8s + GitOps | 有专职运维才上 |

L3+ 或高风险变更：用灰度/金丝雀发布（先放 5-10% 流量观察），回滚脚本保持随时可用。

部署脚本化（一条命令或 CI 流水线完成），禁止"SSH 上去 git pull 再手动重启"——写进 ADR 或运维文档的是脚本，不是口口相传的步骤。

## 三、CI/CD 最小集

流水线（GitHub Actions/GitLab CI）三步，PR 和主分支都跑：

1. lint + 类型检查；
2. 全量测试（带真实测试数据库）；
3. 构建镜像/产物。

主分支合并后自动部署到 prod（或一键手动触发），部署脚本与回滚脚本成对出现（回滚 = 部署上一个成功版本 + 数据库迁移可回退的约定）。

## 四、监控告警最小集

再小的项目也要能回答两个问题：**活着吗？错在哪？**

1. 存活探针：`/healthz`（进程活着）+ `/readyz`（数据库等依赖可达），接 UptimeRobot 之类的免费拨测即可告警。
2. 结构化日志：JSON 日志 + request id 贯穿一次请求；错误日志能按 request id 查上下文。
3. 错误收集：Sentry（有免费档）接上，前端后端都接。
4. 资源底线：磁盘剩余（写满 = 数据库崩）、数据库连接数、内存。云厂商的免费告警规则就够。
5. 慢查询日志（见 quality-attributes.md）。

升级路径（L3+）：Prometheus + Grafana 或云厂商 APM，业务指标（注册数/订单数）进大盘。

## 五、备份与恢复

- 数据库：每日全量 + WAL 归档（云托管数据库打开自动备份即可），保留 ≥ 7 天。
- 对象存储：开版本化或跨区冗余。
- **恢复演练**：没演练过的备份等于没有备份。上线前演练一次"空环境从备份恢复"，把恢复命令写进运维文档。
- 密钥/配置清单（.env 内容、云资源清单）单独安全存放，恢复时要用。

## 六、上线检查清单

- [ ] 域名 + HTTPS 证书配好（自动续期）
- [ ] 环境变量在生产侧配齐（对照 .env.example 逐项核对），密钥不入库
- [ ] 数据库迁移在生产跑过，空库→最新 schema 可从零重放
- [ ] 备份已开且执行过一次恢复演练
- [ ] /healthz、/readyz 可访问，拨测告警生效
- [ ] Sentry 报一个测试错误验证能收到
- [ ] 部署与回滚脚本各跑通一次
- [ ] 日志能看到这次部署的请求
- [ ] CORS/回调域名/第三方控制台里的生产配置（支付、OAuth 等）已切换，不在用测试密钥
