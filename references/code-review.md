# 代码评审（评审者子代理操作手册）

评审的目的不是挑风格毛病，是**在问题变得昂贵之前拦住它**——实现者看不见自己的盲区，评审者的价值就在这双新鲜眼睛。适用范围：标准/完整档的每个任务，实现者交账后、plan.md 勾选前；迷你档与轻量路径不强制。

## 一、评审者的输入

- **任务卡**：T-xx 的 REQ 编号、验收标准、产出清单、DoD。
- **本次变更**：diff 或文件清单——改动范围应与任务卡"产出"字段吻合。
- **蓝图相关章节**：模块职责、API 清单、数据设计、安全底线（blueprint.md §7.1）。

评审者**不需要也不应该**通读整个代码库——只读任务卡、diff 和与变更直接相关的文件。一次评审读不完，通常说明任务粒度超了（>2 天），回去拆任务比硬审更值。

## 二、检查清单（按序过，从最贵的错开始）

| # | 查什么 | 怎么判断 | 级别 |
|---|---|---|---|
| 1 | 验收标准逐条对照 | 任务卡每条 EARS 条目都有实现与验证证明，没有"只做了一半" | 阻塞 |
| 2 | 测试真实有效 | 断言真实校验行为（不是恒真断言、空跑）；EARS 句式映射测试名 | 阻塞 |
| 3 | 蓝图约定一致 | 目录、命名、模块边界、技术栈用法与蓝图一致；未私引入新依赖 | 阻塞 |
| 4 | 安全底线抽查 | 输入校验、授权检查点、注入防护、密钥不入库（对照 quality-attributes.md 七条） | 阻塞 |
| 5 | 越权改动 | diff 里没有任务产出之外"顺手改"的文件；有就要求实现者说明理由 | 阻塞 |
| 6 | 接口与数据一致 | API 签名/返回结构与蓝图 API 清单一致；schema 变更带迁移 | 阻塞 |
| 7 | 文档同步 | API 变了蓝图清单跟着改，决策变了有 ADR | 阻塞 |
| 8 | 性能必查项 | N+1（ORM 预加载）、循环内查询、新查询走索引；蓝图标注过的性能难点为阻塞 | 建议 |
| 9 | 错误处理 | 失效模式有答案的路径有降级/明确报错，不静默吞异常 | 建议 |
| 10 | 可维护性 | 命名可读、无明显重复、魔法数字有解释 | 建议 |

## 三、输出格式

```markdown
评审结论：通过 / 不通过（N 阻塞，M 建议）

阻塞（修复后再审）：
- [文件:行号] 问题描述 → 建议修法

建议（不挡收账，实现者自行裁量）：
- [文件:行号] 问题描述 → 建议修法
```

分级纪律：**阻塞 = 违反验收标准、蓝图约定、安全底线**；**建议 = 不影响正确性的改进**。别把个人偏好当阻塞——风格之争拦不住上线，验收缺口才拦得住。

## 四、修复回路

1. 阻塞问题回给实现者修复，评审者复审——只看修复项，不扩大战线。
2. 最多 2 轮；2 轮后仍有阻塞，升级为主会话按 B 类处理（停下改蓝图或计划再继续）——反复修不好的阻塞通常不是代码问题，是设计问题。
3. 评审通过 → 主会话在 plan.md 勾掉任务、填评审状态，进入下一个任务。
