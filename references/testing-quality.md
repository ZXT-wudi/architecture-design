# 测试策略与质量门禁

测试的目的不是覆盖率数字，是**让验收标准可以被反复验证**——每条需求写下的 WHEN…THE SYSTEM SHALL…，都要有对应的自动化或可重复的手工验证。

## 一、测试分层（金字塔）

| 层 | 测什么 | 量级 | 说明 |
|---|---|---|---|
| 单元测试 | 模块内业务逻辑、纯函数 | 多 | 快、稳定，业务规则的主要守护者 |
| 集成测试 | API 层：请求 → 数据库 → 响应 | 中 | 起真实数据库（测试库/容器），验证 ORM/事务/权限真的对 |
| 端到端（E2E） | 关键用户路径 | 少（3-8 条） | 只测 MUST 需求的核心链路（注册-登录-核心操作），全测维护成本爆炸 |

原则：
- **每条 MUST 需求至少一条自动化测试**；SHOULD 尽量有；COULD 可手工验证。
- 集成测试是性价比最高的一层（直接对着 API 清单和 EARS 验收标准写），不知从哪开始就从它开始。
- 测试不 mock 数据库——mock 了数据库的"集成测试"什么都证明不了。
- EARS 句式天然映射测试用例："当用户提交空标题时，系统应提示…" → 测试名：`提交空标题时返回校验错误且不保存`。

## 二、质量门禁（Definition of Done 的硬部分）

一个任务/一个模块"完成"必须同时满足：

1. 新代码有测试覆盖（对应验收标准的测试通过）；
2. 全量测试通过（不是"我只跑了相关的"）；
3. lint 通过 + 类型检查通过（TypeScript strict / mypy 等，第一天就开 strict）；
4. 手动冒烟：本地跑起来把新功能点一遍；
5. 文档同步：API 变了蓝图 API 清单跟着改，决策变了 ADR 跟着写。

CI 里把这四件事做成一条流水线，红了不许合并——门禁靠机器执行，不靠自觉。

## 三、测试数据与环境

- 测试用例自备数据（fixture/工厂函数），不依赖运行顺序，不共享可变状态。
- 测试数据库每次跑前重建 schema（或事务回滚），保证幂等。
- 需要第三方的场景（支付/短信）：本地/CI 用 mock 或沙箱，预发环境用真实沙箱账号。

## 四、DoD 模板（写进 plan.md 每个任务）

```
任务完成定义：
- [ ] 验收标准逐条验证通过（对应 REQ-xxx 的 EARS 条目）
- [ ] 新增代码有测试，全量测试通过
- [ ] lint + 类型检查通过
- [ ] 手动冒烟通过
- [ ] 文档同步（API 清单 / ADR / README）
```

## 五、上线前测试清单

- [ ] 所有 MUST 需求的验收标准有测试且通过（对照追踪矩阵）
- [ ] E2E 核心链路在类生产环境跑通
- [ ] 失效模式里"不接受风险"的项都有测试（如支付对账任务）
- [ ] 空库/空缓存从零启动跑通（新环境部署演练 = 最好的集成测试）
