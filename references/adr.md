# 架构决策记录（ADR）

## 一、什么是 ADR，为什么写

ADR（Architecture Decision Record）= 一篇一页纸的短文，记录**一次重要的技术选择**：当时有哪些选项、选了什么、为什么、付出了什么代价。

写它的原因只有一个：半年后（或新人入职时），一定有人问"这里为什么用 X 不用 Y"。没有 ADR，答案靠考古和猜；有 ADR，三十秒看完。

## 二、什么时候写

三个条件同时满足才写（满足就写，不要犹豫）：

1. **影响方向**：这个选择影响多个模块或长期演进（技术栈、架构风格、数据库、鉴权方案、消息队列、第三方核心服务）。
2. **难以回退**：换掉它要以周计（换掉一个工具函数不算）。
3. **曾有备选**：当时存在两个以上可行方案，选哪个有过真实的权衡。

不满足三条的（比如"用哪个日期格式化库"）不写，否则 ADR 会膨胀成没人读的日志。

## 三、模板

用 assets/templates/adr.md（内容如下，保持精简）：

```markdown
# ADR-0007: 用 PostgreSQL 全文检索而非 Elasticsearch

- 状态: accepted（proposed / accepted / rejected / superseded by ADR-0012 / deprecated）
- 日期: 2026-09-13
- 决策人: 张三、李四

## 背景（Context）
文章搜索是核心场景（REQ-014）。当前文章量 50 万级，PG FTS 相关性排序不能满足中文分词需求，讨论如何选型。

## 选项（Options）
1. Elasticsearch —— 分词强、生态成熟；代价：新增一套运维、双写同步、内存占用大
2. Meilisearch —— 部署轻、开箱支持中文；代价：生态较新、复杂查询能力弱
3. PG FTS + pg_jieba —— 零新增组件；代价：分词质量与性能天花板明显

## 决策（Decision）
选 2（Meilisearch）。

## 理由（Rationale）
规模在 L2 档次，无法接受 ES 的运维与内存成本；PG 方案分词质量不达标已被 spike（见附录 spike 记录）证实。

## 后果（Consequences）
- 需要维护 PG → Meili 的同步（走 outbox 模式，延迟可接受）
- 若未来搜索需求升级到聚合分析，ES 重新上桌（supersede 本篇）
```

## 四、规则

1. **编号** ADR-0001 起递增，文件名 `ADR-0001-简短标题.md`，永不复用编号。
2. **生命周期**：`proposed`（评审中）→ `accepted`（生效）/ `rejected`（否决，也留着——防止半年后重提同一个坏主意）；被新决策替代时标 `superseded by ADR-xxxx`，**不删除旧篇**。
3. **一个决策一篇**，一次写清；背景要写清"当时知道什么"（今天的常识当年未必）。
4. **决策变了就新增一篇**，旧篇标 superseded——ADR 集合因此成为系统的编年史。
5. 存放：`docs/architecture/decisions/`。蓝图"关键决策"章节列 ADR 索引（编号 + 标题 + 状态）即可，不复制正文。
6. 存量项目进入维护前，先扫一遍是否已有 `docs/decisions/`、`docs/adr/`、`adr/` 等目录（常见变体），有就沿用人家的位置和格式，别另起炉灶。

## 五、和需求追踪的关系

重要 ADR 的背景一节要引用 REQ 编号（"搜索是核心场景（REQ-014）"）——需求变了驱动重审决策，决策变了在需求文档里标注影响，双向链起来。
