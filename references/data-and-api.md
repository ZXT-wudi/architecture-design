# 数据建模与 API 设计

## 一、实体识别与建模

1. 从需求文本里圈名词（文章、评论、订单、商品），动词是关系（发布、属于、包含）。名词≠实体：先列候选，合并同义、剔除只是属性的东西。
2. 每个实体回答四件事：**唯一标识**（谁生成）、**生命周期**（创建后状态怎么流转）、**归属**（删了它附属数据怎么办）、**多对多关系**（中间表叫什么）。
3. 画 ER 图（Mermaid erDiagram，规范见 diagram.md）。
4. 状态机优先：凡有状态流转的实体（订单：待支付→已支付→已发货…；文章：草稿→已发布→已下架），把状态机画出来——允许的状态迁移写清楚，非法迁移在设计层就堵住。
5. 通用字段一次性定好：`id`（UUID 或自增，二选一并说明）、`created_at`、`updated_at`、`deleted_at`（软删约定）。审计需求（谁改的）→ `created_by/updated_by`。

## 二、存储选型速查

| 数据形态 | 选什么 | 说明 |
|---|---|---|
| 结构化、有关系、要事务 | PostgreSQL（默认） | 90% 场景的正确答案 |
| 大量文本/图片等大对象 | 对象存储（S3/OSS），库里只存 key | 别把 5MB 文件塞进数据库 |
| 全文搜索 | 先 PostgreSQL FTS，量级/相关性要求上来换 Meilisearch/ES | |
| 缓存/会话/计数器 | Redis | 有真实读压力才引入 |
| 弱结构、嵌套文档 | 先问能不能建模成关系表；真不能再 MongoDB | "不知道字段长啥样"才轮到文档库 |
| 时序/日志 | TimescaleDB / 专门时序库 | |
| 向量检索 | pgvector 起步 | 量级上来再换专用库 |

原则：**一个关系库起步，新增存储类型必须说明关系库哪里不行**（写进 ADR）。

### 建模细节

- 规范化起步（3NF），为读性能做的反规范化（冗余字段、汇总表）**每处都写注释说明来源**，否则半年后没人敢动。
- 金额用整数分/定点数，不用浮点。时间一律 UTC 存储，展示层转时区。
- 预估大表（百万行级）提前设计索引：把"查询 WHERE/ORDER BY 哪些字段"列表对照建索引，API 清单就是索引清单的来源。

## 三、API 设计规范

### RESTful 约定

- 资源用名词复数：`GET /articles`、`POST /articles`、`GET /articles/{id}`、`PATCH /articles/{id}`、`DELETE /articles/{id}`。动作类操作用子资源动词：`POST /articles/{id}/publish`。
- 版本化：`/api/v1/` 前缀，第一天就加。
- 分页：`?page=1&size=20` 或游标 `?cursor=xxx`，响应里带 `total`（或游标方式带 `next_cursor`）。**所有列表接口默认分页，禁止裸列表。**
- 过滤排序：`?status=published&sort=-created_at`，白名单允许的字段。
- 错误响应统一结构：`{"error": {"code": "VALIDATION_ERROR", "message": "...", "details": [...]}}`，错误码表写进蓝图。
- 幂等：POST 创建可带客户端生成的 `Idempotency-Key`；所有写操作在重试时必须安全（支付类接口必须有）。

### API 清单格式（写进蓝图）

| 方法+路径 | 用途 | 鉴权 | 实现的 REQ |
|---|---|---|---|
| POST /api/v1/articles | 创建文章 | 登录用户 | REQ-003 |
| GET /api/v1/articles?status= | 分页查文章列表 | 公开 | REQ-001 |
| POST /articles/{id}/publish | 发布文章 | 作者本人 | REQ-005 |

"实现的 REQ"列就是 API ↔ 需求的对账依据——列完回头看，有 REQ 没对应任何 API/任务，就是漏了。

### 权限模型

1. 先列角色：匿名、注册用户、作者、管理员……（来自需求"用户与角色"维度）。
2. 每个角色的能力表：对每类资源能做什么（看/建/改/删/审）。
3. 实现默认 RBAC：用户-角色-权限三张标准表。出现"满足条件 X 的用户可以…"且条件不可枚举时才考虑 ABAC。
4. **后端逐接口强制鉴权**，前端隐藏入口只是体验不是安全。多租户场景：所有查询必须带租户过滤，这一条建议做成数据层强制约定而不是靠每个查询自觉。

## 四、对外接口的额外考虑

- 第三方要调你的 API 时：API Key + 签名/限流 + 独立版本承诺（v1 不轻易破坏兼容），这些是需求不是优化。
- 调第三方 API 时：超时（必须有，默认 5-10s）、重试（指数退避、只重试幂等操作）、熔断降级、密钥不进代码库——写进蓝图的集成章节。
