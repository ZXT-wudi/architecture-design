# 技术选型

选型的第一输入是**团队会什么**，第二才是技术先进性。选型内耗（反复对比框架一周不写码）比选错更贵——本文件给默认答案，让你快速收敛。

## 一、选型原则

1. **默认推荐优先**：没有明确理由偏离时，用下表的"默认"列。它们是生态最大、资料最多、踩坑文档最全的选择。
2. **团队技能压倒一切**：用户熟 Python 而不熟 Node，后端就用 Python。强扭的团队学新栈，延误以月计。
3. **YAGNI**：不为想象中的规模选型。L1 档次不需要消息队列、不需要 K8s、不需要分库分表。
4. **锁定版本**：定栈时写明具体版本（如 PostgreSQL 16、Node 22 LTS、Next.js 15），写入蓝图。版本漂移是环境问题的头号来源。
5. **偏离要有 ADR**：不用默认栈而选别的（无论什么原因），落一篇 ADR 记录权衡。
6. **组件库看对标**：UI 组件库/设计系统的最终选择，对照需求"界面与体验"维度的答案（偏好、对标站点、品牌规范）确认——默认推荐只是起点，给用户看过实例再定。

## 二、分场景默认栈

### Web 应用（前后端一体或分离）

| 层 | 默认 | 备选 | 备选何时更好 |
|---|---|---|---|
| 前端框架 | React + TypeScript | Vue 3 | 团队更熟 Vue；中文生态场景 |
| 元框架 | Next.js | Nuxt / 纯 Vite SPA | 需要强 SEO 用 Next/Nuxt；纯后台管理用 Vite SPA 更简单 |
| UI 组件库 | shadcn/ui + Tailwind | Ant Design | 中文中后台场景 AntD 成熟度更高 |
| 后端（一） | Node.js (NestJS/Fastify) | —— | 与前端同语言，全栈一致 |
| 后端（二） | Python (FastAPI) | Django | 团队熟 Python；Django 自带 admin/ORM/鉴权，管理后台更快 |
| 后端（三） | Java (Spring Boot) | Go (Gin/Echo) | 大型企业团队既有 Spring 资产；Go 适合高并发小服务 |

### 移动端

| 场景 | 默认 | 说明 |
|---|---|---|
| 同时要 iOS + Android，团队是 Web 背景 | React Native（Expo） | 一套代码两端 |
| 强动画/高性能/图形 | 原生（Swift/Kotlin） | 跨端框架的动画性能是长期痛点 |
| 只要小程序 | 微信原生或 Taro/uni-app | 按是否也要 H5/App 决定 |
| 简单内容展示类 App | 先做 PWA 验证需求 | 最便宜的验证方式 |

### 数据层

| 需求 | 默认 | 备选与时机 |
|---|---|---|
| 主数据库 | PostgreSQL 16 | MySQL（团队更熟/DBA 只会 MySQL）；SQLite（L1 单机且无并发写） |
| 缓存 | Redis | 有 L2 及以上才引入；L1 直接怼数据库 |
| 搜索 | PostgreSQL 全文检索起步 | 数据量到百万级或需要中文分词质量 → Meilisearch/Elasticsearch |
| 消息队列 | 先用 PostgreSQL 表轮询/定时任务 | 真有削峰/解耦/重试需求 → Redis Streams 起步 → RabbitMQ/Kafka |
| 对象存储 | 云厂商对象存储（S3/OSS/COS） | 本地磁盘（仅限单机私有化） |
| 时序数据 | PostgreSQL + TimescaleDB | 大量监控点 → 专门时序库 |

### 部署

| 档次 | 默认 | 说明 |
|---|---|---|
| L1 | PaaS（Vercel/Railway/Render）或单台 VPS + Docker Compose | 零运维起步 |
| L2-L3 | 云主机 + Docker Compose 或轻量 K8s 托管 | 有多实例/主从需求后 |
| L4 | K8s + 云托管数据库 | 有专职运维时才考虑 |

## 三、权衡表写法

给用户展示选型时用这个格式（放蓝图"技术栈"章节）：

```
| 方案 | 优点 | 代价 | 适用条件 |
| Next.js 全栈 | 一套语言；部署简单；SSR 利于 SEO | 重逻辑后端不如独立后端清晰 | 内容型/中小规模 Web |
| Vite SPA + FastAPI | 前后端解耦；Python 生态利于数据处理 | 两套工程；跨域/CORS 处理 | 团队 Python 强；后端有算法/数据任务 |
```

规则：每方案 2-3 条优点 + 2-3 条代价，写真实代价（没有代价的方案说明没想清楚）。给推荐结论，不要把选择原样抛回给用户。

## 四、决策顺序（避免选型内耗）

1. 用户有强偏好/既有资产？→ 用他的，落 ADR，结束。
2. 没偏好 → 对号入座取默认栈，展示权衡表知会用户，结束。**整轮选型控制在一次对话内完成。**
3. 用户纠结两个方案 → 帮他定：看团队技能 > 看场景匹配 > 抛硬币。纠结本身说明两个都够用。
